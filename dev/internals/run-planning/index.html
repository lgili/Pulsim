    How a run is planned¶

    pulsim.simulate() is three steps (add-kernel-simulation-object, Stage A):

    def simulate(builder, t_end=None, dt=None, **kw):
    plan = _plan_run(builder, t_end, dt, **kw)       # resolve everything once
    return _finalize(_ENGINES[plan.engine](plan), plan)
    step function what it does
    plan _plan_run every keyword resolved (LoadedCircuit, the solver= bundle, validation); the preflight ties (_apply_ties, the one place a run changes its circuit); resume_from and the initial state; the drive (_compose, then _compose_for the engine landed on); the route (_route: the option x engine table, the variable-step blockers, the 'auto' rule); the engine's kernel options
    run _run_pwl / _run_trbdf2 / _run_dsed build the kernel object or cache, attach what needs the run's own cache, run; they read only the plan
    finalize _finalize the result's handles (_builder, plan, engine_used, engine_route_reason), the post-run checks and warnings

    The plan is an immutable pulsim._plan.SimPlan: engine, engine_asked, route_reasons, features, step (FixedStep / VariableStep / ExactStep), newton, events, initial, drive, and resolved_from (one entry per keyword: explicit, solver, yaml or default). It is not pulsim.RunPlan, the circuit record a result carries (result.plan); the plan holds that one as circuit_plan.

    Every record of the plan is a typing.NamedTuple: a tuple with no __dict__, so a field cannot be set or deleted and no attribute can be added (AttributeError). Not frozen dataclasses: their __init__ pays one object.__setattr__ per field, and the plan is built on every simulate() call (task 7.2 keeps that call's fixed overhead near its pre-Stage A value; test_simulate_overhead.py is a local bytecode ratchet). simulate() builds the records with tuple.__new__ and every field in order, and passes its keywords to _plan_run and _route positionally; test_run_plan.py checks each of those name lists against the signature and each record's arity. The objects the plan holds (the builder, the control plan, the user's callables) are not immutable.

    The rule: put it in the plan¶

    simulate() used to be one 1 800-line function with three early returns, one per engine. A check, a default or an initial condition written below the first return applied to one engine only, silently: builder ICs, a resume_from check and a preflight report were each found missing on one engine this way. Now:

    • Anything that must hold for every engine goes in _plan_run, before the route.
    • An engine runner reads only plan (test_engine_branches_read_only_the_plan parses them with ast); a new simulate() keyword fails test_plan_resolves_every_kwarg until it is planned.
    • Behaviour that legitimately differs per engine is an explicit per-engine entry of the plan or of _finalize, never a position in the code.

    Time: t_start is an absolute label¶

    t_start labels the run's first instant on the ONE clock every input is written on. Every time-dependent object — the gate and its edge oracle, b_extra_fn, the circuit's sine / pulse / PWM / PWL sources, control-tick callables, recorder windows and periods, loss-event and re-initialisation instants — is evaluated or reported at absolute t on every engine, so a run on [t_start, t_end] started from the state at t_start equals the tail of the run on [0, t_end] (which is what a resume means). Two deliberate choices: a fresh run's control-tick grid starts at t_start (t_start + k*T, the ticks' documented contract; a resume continues the first run's grid from the snapshot), and the stored state at t_start is the caller's initial_state.

    An engine whose clock runs from 0 shifts EVERY input it hands a time to in one place — where the plan hands it the drive — and shifts every output back. Today that is the exact engine on a fresh run (not a resume: it resumes on the absolute clock): _run_dsed wraps the gate (and its edge oracle) and b_extra_fn (_dsed_dispatch.on_absolute_clock), and _result_from_native relabels the times, event times, re-initialisation records, mode diagnostics and the output budget (the loss events in the binding, t_offset). What cannot be shifted from Python is refused by name: the circuit's own time-varying sources (the native adapter evaluates them on the engine's clock; feature='t_start'), controllers (_compose_for), the snapshot of such a run (final_snapshot.invalid_reason). The test is test_tstart_time_base.py.

    What still differs per engine, and how the release makes it one¶

    Stage A moved code without changing a result, a warning or a refusal. The blocks that were per engine (DECISIONS 23 of add-kernel-simulation-object) now each have ONE release behaviour behind a mechanism whose default is today's (DECISIONS 26): a keyword resolved in the plan (None = today), a library default in pulsim._plan the number-changing release flips (benchmarks/tools/next_defaults.py, section PLAN), or "kept per engine" where the difference is the engine's own.
